# متطلبات تطبيق الأندرويد — «خطوة صحية»

> تطبيق شخصي لطالب التخرج **يوسف سليمان** — كلية التربية الرياضية
> الغرض: أداة ميدانية لإجراء تجربة «تأثير الجهد البدني المنظم على معالجة السكري»، ووسيلة عرض أمام لجنة المناقشة لإثبات صحة الفرضية بأرقام ومخططات حية.
> هذا المستند هو **مرجع التطوير الرسمي** (عقد المتطلبات): أي ميزة تُبنى في التطبيق يجب أن تطابق ما هو مذكور هنا، وما لا يوجد هنا فهو من الإضافات المقترحة القابلة للنقاش.

---

## 1) نظرة عامة

التطبيق يعمل **دون إنترنت بالكامل** (Offline-First) ويخزن كل شيء في قاعدة بيانات SQLite محلية على هاتف الطالب. الواجهة عربية بالكامل مع دعم RTL من اليمين إلى اليسار. يقوم التطبيق بشيء واحد جيدًا: إدارة تجربة مقارنة بين **مجموعة خاضعة لبرنامج رياضي منظم** و**مجموعة ضابطة بدون رياضة**، عبر قياس يومي لسكر الدم لكل مريض، ثم عرض النتائج والإحصاءات التي تثبت أو تنفي أثر الجهد البدني.

الاسم المقترح للتطبيق: **«خطوة صحية»** (بدائل مقترحة: «رياضي وسكري»، «الجهد العلاجي»).
اسم الحزمة المقترح: `com.yousef.stephealth`.

### الجمهور والمستخدم الوحيد

- الطالب يوسف نفسه: يدير التجربة ويُدخل القياسات.
- لجنة المناقشة: تتفرج فقط على شاشة العرض (الوضع التجريبي أو نتائج حية).

## 2) الوضعان الأساسيان

| | الوضع الحقيقي (Real Mode) | الوضع التجريبي (Demo Mode) |
|---|---|---|
| المصدر | قاعدة البيانات المحلية للتطبيق | ملف قاعدة بيانات `.db` مستورد من مجلدات الهاتف |
| الكتابة | كاملة (إضافة وتعديل) | **للقراءة فقط** — لا يُمس المشروع الحقيقي إطلاقًا |
| الغرض | إجراء تجربة حقيقية | عرض نموذج افتراضي أمام اللجنة |
| العلامة الظاهرة | عادي | شريط ثابت أعلى الشاشة بلون مميز مكتوب عليه «وضع تجريبي — بيانات افتراضية» |

**القرار التصميمي المعتمد (العزل الكامل):** الوضع التجريبي يعمل في «حاوية معزولة» — يُنسخ الملف المستورد إلى مجلد داخلي خاص بالعرض التجريبي، وتُفتح شاشات المشروع والمرضى والنتائج منفصلة تمامًا عن قاعدة البيانات الحقيقية، مع شريط تحذير دائم. عند الخروج من الوضع التجريبي يُحذف الملف المنسوخ ويعود التطبيق لحالته الحقيقية كما لم يحدث شيء. لا يوجد أي احتمال لخلط بيانات النموذج الافتراضي مع التجربة الحقيقية.

## 3) دورة حياة المشروع الحقيقي

1. من الشاشة الرئيسية زر بارز: **«بدء مشروع حقيقي»**.
2. معالج إنشاء المشروع يسأل بالترتيب:
   - **اسم المشروع** (إلزامي).
   - **مدة المشروع** بالأسابيع (افتراضي 12 أسبوعًا، مدى مقبول 4–26 أسبوعًا) — تتحول داخليًا إلى أيام (الأسابيع × 7).
   - **وسم/وصف المشروع**: نص حر، **افتراضيًا** «تأثير الجهد البدني المنظم على معالجة السكري»، قابل للتعديل بحرية.
3. عند الإنشاء تُسجَّل حالة المشروع: **«قيد الإنشاء»** (مرحلة تجهيز المرضى).
4. يدخل الطالب للمشروع ويضيف المرضى عبر المعالج (البند 4). عند إدخال أول قياس فعللي لأي مريض تتحول الحالة تلقائيًا إلى **«جاري»**، وعند انقضاء المدة (أو ضغط الطالب «إنهاء وتجميع النتائج») تتحول إلى **«مكتمل»**.
5. داخل صفحة المشروع: ملخص علوي (الاسم، الوسم، الحالة بشارة ملونة، الأيام المنقضية/المتبقية، عدد المرضى في كل مجموعة، نسبة الالتزام بالقياس).

## 4) معالج إضافة مريض

زر «إضافة مريض» داخل صفحة المشروع يفتح معالجًا متعدد الخطوات (Wizard) يسأل بالترتيب:

| الخطوة | الحقل | إلزامي | ملاحظات |
|---|---|---|---|
| 1 | **المجموعة** | نعم | خياران واضحان بألوان مختلفة: «مع برنامج رياضي (خاضع للمراقبة)» أو «بدون رياضة (مجموعة ضابطة)» |
| 2 | **الاسم** | نعم | نص حر، لا يُسمح بالتكرار داخل المشروع نفسه |
| 3 | **العمر** | نعم | 18–90 سنة |
| 4 | **الجنس** | نعم | ذكر / أنثى |
| 5 | **الوزن والطول** | لا | يُحسب BMI تلقائيًا ويظهر مع تصنيفه |
| 6 | **السكر التراكمي الأساسي HbA1c** | لا | رقم عشري مثل 8.4 — مفيد لربط النتائج بالأطروحة |
| 7 | **ملاحظات صحية** | لا | نص حر (أدوية، أمراض مصاحبة…) |

زر **«حفظ»** في النهاية، ثم يعود المعالج فارغًا لإضافة المريض التالي مباشرة (لتسريع إدخال 30 مريضًا مثلًا)، مع عدّاد حي «أُضيف: 12 مريضًا». يمكن الحذف أو التعديل لاحقًا من صفحة المريض (الحذف يتطلب تأكيدًا مزدوجًا).

## 5) القياسات اليومية لسكر الدم

- من **صفحة المريض**: زر «تسجيل قياس اليوم» بارز، والقيمة بالوحدة **mg/dL** (مدى مقبول 40–600، وتحذير ألوان خارج المدى الطبيعي).
- **التاريخ والوقت يُأخذان تلقائيًا من ساعة الهاتف** عند الضغط على حفظ — لا إدخال يدوي للتاريخ في القياس اليومي العادي.
- **قياس واحد لكل يوم** لكل مريض (إعادة الإدخال في نفس اليوم تعرض «تعديل القياس الموجود» وليس إضافة قيمة ثانية).
- **التسجيل المتأخر**: في أي يوم فائت يمكن فتح قائمة «الأيام الفائتة» وإدخال قيمة بتاريخ اليوم الفائت (يُعرض التقويم)، أو **تعديلها لاحقًا**، أو **تركها فارغة نهائيًا**.
- **ممنوع منعًا باتًا**: تعويض القيمة الفارغة بـ0 أو بأي رقم افتراضي وقت الإدخال — القيمة الفارغة تبقى فارغة في قاعدة البيانات، لأن أي تعويض يدوي يفسد النتائج. التعويض (إن وُجد) يحدث **فقط داخل محرك التحليل** وفق القاعدة الموثقة في البند 6.
- صفحة المريض تعرض تقويمًا شهريًا ملونًا: يوم مسجل (أخضر/أحمر حسب القيمة)، يوم فائت (رمادي)، يوم مستقبلي (غير قابل للإدخال).

## 6) قواعد سلامة النتائج (حرجة — تُنفذ حرفيًا)

هذه القواعد هي قلب معالج «فحص النتائج» ولا يجوز الالتفاف عليها:

1. **حد النقص المسموح**: لا يمكن قبول نقص يزيد على **قياسين** لكل مريض طوال مدة البرنامج. إذا ناقص الثالث → يتوقف المعالج ويُظهر رسالة «تعذّر فحص النتائج: المريض فلان ينقصه 3 قياسات — الحد المسموح قياسان» مع انتقال مباشر لتقويم المريض لتسجيل الفائت.
2. **قاعدة التتابع**: لا يمكن قبول القياسين الناقصين في **يومين متتاليين**. أي فجوة يومين متتاليين تعامَل معاملة النقص الزائد (رفض الفحص مع رسالة واضحة تذكر السبب: «يومان متتاليان بدون قياس في 12–13 مارس»).
3. **آلية التعويض عند التحليل فقط**: القيمة الفارغة داخل سلسلة قياسات تُستبدل عند الحساب بـ**المتوسط الحسابي للقياسين الحقيقيين المجاورين (قبلها وبعدها)** — استقراء خطي بنقطة واحدة (Linear Interpolation). المثال: قياسا 12 و16 مارس حقيقيان و13 مارس فارغ → يُحسب 13 مارس = (قيمة 12 + قيمة 16) ÷ 2 وقت التحليل فقط.
4. **الفجوة عند طرفي السلسلة**: إذا كان القياس **الأول** أو **الأخير** في البرنامج فارغًا فلا يوجد «قياس قبله/بعده» للتوسط → **يتوقف معالج الفحص فورًا بسبب نقص المعلومات** برسالة تحدد المريض واليوم والخياران (تسجيل القيمة أو استبعاد المريض من التحليل النهائي بعلم الطالب).
5. لا يتم أي تعديل على قاعدة البيانات أثناء التحليل — التعويض يحدث في الذاكرة فقط عند الحساب.
6. لوحة «جاهزية الفحص» داخل المشروع تعرض لكل مريض: عدد الفجوات، هل يستوفي القواعد (✓/✗) والسبب — حتى يعرف الطالب وضعه قبل نهاية التجربة لا بعدها.

## 7) التنبيهات اليومية

- إشعار يومي في **الساعة 8:00 مساءً** بتوقيت الهاتف أثناء حالة «جاري».
- نص الإشعار يذكر **عدد القياسات الناقصة اليوم**: «لديك 4 قياسات غير مسجلة اليوم — 2 من المجموعة الرياضية و2 من الضابطة». وفي حال اكتمال الجميع: «اكتملت قياسات اليوم ✓».
- الضغط على الإشعار يفتح شاشة «القياسات المعلقة اليوم» بقائمة المرضى الناقصين وزر تسجيل سريع بجانب كل واحد.
- التنبيهات تعمل عبر WorkManager بحيث تنجو من إعادة تشغيل الهاتف، مع إعادة جدولة تلقائية، ويمكن تغيير وقت التنبيه من الإعدادات (افتراضي 20:00) وتعطيله مؤقتًا (مثلًا يوم سفر) دون فقدان القاعدة.

## 8) شاشة النتائج (تتوفر في أي لحظة — حتى قبل انتهاء البرنامج)

تعرض النتائج **الحالية** أي من اليوم الأول حتى اليوم المحدد الأخير المسجل. تحتوي قائمتين منسدلتين في أعلى الشاشة:

### القائمة المنسدلة الأولى: اختيار مريض
تعرض **مخططًا خطيًا** لقياسات المريض المختار يومًا بيوم، مع:
- خط القيم الحقيقية، ونقاط القيم المعوضة ظاهرة بنمط مختلف (معين مفرغ) مع تلميح «قيمة معوضة حسابيًا».
- خط مرجعي للنطاق الطبيعي الصيامي (70–130 mg/dL) بمنطقة مظللة.
- خط اتجاه (Trendline) بحساب الانحدار الخطي البسيط يوضح الميل العام (ينخفض أم يرتفع).
- شارة ملخص أعلى المخطط: متوسط الفترة، أعلى/أدنى قيمة، نسبة التغير من أول قياس حتى آخر قياس.

### القائمة المنسدلة الثانية: اختيار الفئة (كل المرضى / الخاضعون للرياضة / غير الخاضعين)
هذه القائمة **لا تغيّر قائمة المرضى** ولا المخطط المختار أعلاه — هي تُبدّل **قسم الإحصاءات الجماعية** المعروض أسفل الشاشة حسب الفئة المختارة:

1. **منحنى متوسط التغير اليومي النسبي**: لكل يوم د، يُحسب لكل مريض التغير النسبي من قياسه المرجعي (متوسط أول يومين مسجلين): `تغير اليوم = (قياس اليوم − المرجعي) ÷ المرجعي × 100`، ثم يُؤخذ متوسطه للمرة المختارة. مثال مطابق لمثال صاحب المتطلبات: اليوم الأول 0.00 لكل الجميع، اليوم الثاني متوسط الفئة +0.15 (بعضهم انخفض 1% وبعضهم ارتفع وثابت)، وهكذا تراكميًا.
2. **مخطط أعمدة (Bar Chart)** لمتوسط التغير اليومي عبر الأيام، بأعمدة ملونة دلاليًا (أخضر انخفاض، أحمر ارتفاع، رمادي ثبات ±0.1%).
3. **توزيع الحالة اليومية**: نسبة من تحسن / ثابت / ارتفع في الفئة لكل يوم (مخطط أعمدة مكدس).
4. **بطاقات ملخص للفئة**: متوسط الانخفاض النهائي %، متوسط السكر الحالي، عدد الأيام المسجلة، نسبة الالتزام، أفضل وأضعف مريض تحسنًا.
5. **مقارنة الفئتين وجانبًا لجانب** (عند اختيار «كل المرضى»): منحنى الخاضعين مقابل غير الخاضعين في نفس المحاور، والفرق بينهما يوم بيوم — هذا المخطط تحديدًا هو «إثبات الفرضية» أمام اللجنة.

### حسابات إحصائية إضافية مدمجة (لمسات التطبيق)
- **المتوسط ± الانحراف المعياري** لكل مجموعة في كل أسبوع (جدول أسبوعي قابل للتمرير).
- **فرق المتوسطات بين الفئتين** مع مؤشر بسيط للفروق (نُعرض كفرق واضح بألوان دون ادعاء دلالة إحصائية رسمية — النقاط p-value تُترك للتحليل الخارجي SPSS في الأطروحة).
- **معدل الاستجابة**: نسبة مرضى الفئة الذين انخفض متوسطهم ≥ 5%.
- **خط زمني مصغر (Sparkline)** في بطاقة كل مريض داخل قائمة المشروع.

## 9) التصدير

- **تصدير CSV** لكل بيانات المشروع (المرضى + القياسات الخام) بترميز **UTF-8 مع BOM** ليفتح في Excel بالعربية دون تشويه، وأسماء الأعمدة إنجليزية للتوافق مع SPSS.
- **تصدير تقرير PDF** من صفحة النتائج: صفحة غلاف مصغرة (اسم المشروع والوسم والمدة)، ملخص الأرقام، المخططات الرئيسية كصور، وجدول المرضى — عبر مكتبة PdfDocument الأصلية أو مكتبة عربية داعمة للاتجاه.
- التصدير إلى مجلد التنزيلات + زر مشاركة مباشر (WhatsApp/بريد) عبر Intent.

## 10) الوضع التجريبي خطوة بخطوة

1. من الشاشة الرئيسية زر «عرض نموذج تجريبي».
2. خياران: اختيار ملف من **مجلدات الهاتف** (SAF — Storage Access Framework، فلتر `*.db`)، أو اختيار أحد **النماذج المرفقة مسبقًا** داخل التطبيق (ملفات databases المرفقة في هذا المجلد).
3. التطبيق يتحقق من الملف (بنية الجداول + نسخة المخطط) ثم ينسخه إلى حاوية العزل ويدخل شاشات العرض مع شريط «وضع تجريبي» الدائم.
4. كل شاشات المشروع والمرضى والنتائج تعمل **للقراءة فقط**.
5. زر «إنهاء العرض التجريبي» في كل شاشة يعيد فورًا للشاشة الرئيسية ويحذف الحاوية المعزولة — والمشروع الحقيقي لم يُلمس، والقيم تعود كما كانت تمامًا.

## 11) الإضافات الاحترافية المقترحة (لمسات المطور)

- **قفل PIN اختياري**: بيانات المرضى شخصية حساسة — قفل سريع من 4 أرقام عند فتح التطبيق (قابل للتعطيل).
- **نسخة احتياطية كاملة**: تصدير/استيراد قاعدة البيانات الحقيقية كملف واحد (نفس آلية الاستيراد) — حماية من فقدان الهاتف.
- **أرشيف المشاريع**: يمكن أن يوجد أكثر من مشروع (تجربة تخرج + تجارب تجريبية لاحقة)، وعرضها كمشاريع مكتملة قابلة للمقارنة.
- **شاشة الترحيب الأولى** تشرح التطبيق بثلاث بطاقات (مشروع حقيقي / عرض تجريبي / الأدوات) — مفيدة جدًا أمام اللجنة.
- **وضع ليلي** كامل ومقاسات خط قابلة للتكبير.
- **وضع العرض الأمامي**: زر «عرض للجنة» يجعل التطبيق ملء الشاشة بخط أكبر ويخظر عناصر الإدخال — مناسب لإسقاط الشاشة على البروجكتر.
- **تحقق ذكي من القيم**: عند إدخال قيمة شاذة جدًا (مثل 480) يظهر تنبيه «قيمة مرتفعة جدًا — هل أنت متأكد؟» قبل القبول.
- **إحصاء التزام الأسبوع الماضي** في لوحة المشروع مع نجوم ⭐ لكل مريض ملتزم 100%.

## 14) مخطط قاعدة البيانات الموحد (Schema v1)

```sql
CREATE TABLE projects (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  name          TEXT NOT NULL,
  tag           TEXT DEFAULT 'تأثير الجهد البدني المنظم على معالجة السكري',
  status        TEXT NOT NULL DEFAULT 'قيد الإنشاء',  -- قيد الإنشاء / جاري / مكتمل
  mode          TEXT NOT NULL DEFAULT 'real',          -- real / demo
  start_date    TEXT,                                   -- ISO yyyy-mm-dd
  duration_days INTEGER NOT NULL DEFAULT 84,
  created_at    TEXT NOT NULL
);

CREATE TABLE patients (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  project_id      INTEGER NOT NULL REFERENCES projects(id),
  name            TEXT NOT NULL,
  age             INTEGER,
  gender          TEXT,               -- ذكر / أنثى
  group_type      TEXT NOT NULL,      -- sports / control
  weight_kg       REAL,
  height_cm       REAL,
  baseline_hba1c  REAL,
  end_hba1c       REAL,
  notes           TEXT,
  created_at      TEXT NOT NULL
);

CREATE TABLE measurements (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  patient_id  INTEGER NOT NULL REFERENCES patients(id),
  date        TEXT NOT NULL,          -- ISO yyyy-mm-dd
  value_mgdl  REAL NOT NULL,          -- mg/dL
  entered_at  TEXT NOT NULL,
  UNIQUE(patient_id, date)
);

CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT);
```

فهارس مطلوبة: `measurements(patient_id, date)` فريد، و`patients(project_id)`.
